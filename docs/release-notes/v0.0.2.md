# Panko 0.0.2

Panko turns infrastructure code into a self-service API. This experimental release makes Panko
installable without a repository checkout: one `panko-server` binary for every runtime role with
Metacontroller embedded, a published Helm chart, and `panko dev up` / `panko install` in the CLI.

## Try it

```sh
brew install hingst-it/tap/panko
# or: mise use -g github:hingst-it/panko@0.0.2
# or: asdf plugin add panko https://github.com/hingst-it/asdf-panko.git && asdf install panko 0.0.2
panko dev up
```

`panko dev up` needs a running Docker engine on macOS or Linux. It creates a dedicated k3d lab
(installing the pinned k3d privately after you agree), pulls the published images, and maps the
API to `http://127.0.0.1:8081`. Follow the
[quickstart](https://github.com/hingst-it/panko/blob/v0.0.2/docs/quickstart.md) to create your
first database. The public example module needs no deploy key or cloud account.

For an existing cluster: `panko install --kubeconfig ./config --context my-cluster`, or Helm:

```sh
helm install panko oci://ghcr.io/hingst-it/charts/panko --version 0.0.2 \
  --namespace panko-system --create-namespace
```

Argo CD, Flux and rendered-manifest examples pinned to this release are in
[GitOps](https://github.com/hingst-it/panko/blob/v0.0.2/docs/gitops.md).

## Artifacts

| Artifact | Reference |
| --- | --- |
| CLI archives (macOS, Linux, Windows; AMD64, ARM64) | `panko_0.0.2_<os>_<arch>.tar.gz` / `.zip` |
| Remote agent binary (Linux AMD64, ARM64) | `panko-server_0.0.2_linux_<arch>.tar.gz` |
| Helm chart | `oci://ghcr.io/hingst-it/charts/panko:0.0.2`, `panko-0.0.2.tgz` |
| Server image (every in-cluster role) | `ghcr.io/hingst-it/panko-server:0.0.2` |
| Module mirror image | `ghcr.io/hingst-it/panko-module-mirror:0.0.2` |
| Remote agent image (OpenTofu 1.11.7, git) | `ghcr.io/hingst-it/panko-agent:0.0.2` |
| Checksums | `SHA256SUMS` (checksums, not signatures) |

Images are multi-architecture (Linux AMD64 and ARM64) and pullable without credentials. Image and
chart tags have no `v` prefix.

## Upgrading from 0.0.1

A v0.0.1 installation moves to the chart with one documented procedure: back up, pause, remove the
separate Metacontroller, `panko install --take-ownership`, resume. Resources keep their identity,
state, finalizers, connection Secrets and tokens, and are not re-applied. See
[upgrading](https://github.com/hingst-it/panko/blob/v0.0.2/docs/upgrading.md); a rollback means
restoring the backup into a fresh v0.0.1 installation, which is only safe before resources changed.

Compatibility changes: the short name `db` is gone (`kubectl get databases.platform.example.com`
or `kubectl get panko`), image tags lose their `v`, and `controller.replicas` must be 1.

## Limitations

- Experimental: APIs and configuration may change. Not production-grade isolation: static team
  tokens, a shared PostgreSQL administrator credential, no OIDC.
- One controller replica; no high availability. Leader election exists but is not validated.
- PostgreSQL databases are the only resource type. OpenTofu only; Terraform CLI execution is not
  tested.
- Drift checks report and never repair. Failed applies are retried only on request.
- Replacing a CA is a manual two-step trust rollover; the setup Job warns a year in advance.
- `panko dev` needs Docker on macOS or Linux; Podman is not supported.
- Moving API groups, contract versions and module-revision policies are deferred
  ([naming](https://github.com/hingst-it/panko/blob/v0.0.2/docs/naming.md)).
