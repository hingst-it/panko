# Upgrading, migration, backup and recovery

This page is the authoritative procedure for moving a v0.0.1 installation to v0.0.2, for routine
upgrades of a v0.0.2 installation, and for backup, restore and recovery. Panko is experimental:
rehearse every step on a disposable copy first, and keep a backup.

`test/release_acceptance.py migrate` rehearses the v0.0.1 → v0.0.2 procedure below on a
disposable cluster built from the `v0.0.1` tag; the [release notes](release-notes/v0.0.2.md)
record its result.

## What changes from v0.0.1 to v0.0.2

| Area | v0.0.1 | v0.0.2 |
| --- | --- | --- |
| Installation | `make bootstrap build deploy` from a checkout, `kubectl apply` | Helm chart `oci://ghcr.io/hingst-it/charts/panko` through `panko install`, `panko dev up`, Helm, Argo CD or Flux |
| Metacontroller | separate Helm release in namespace `metacontroller` | embedded in `panko-server controller` (Deployment `infra-runners/database-hook`) |
| Images | five per-component images, tags with `v` (`v0.0.1`) | `panko-server`, `panko-module-mirror`, `panko-agent`, tags without `v` (`0.0.2`) |
| CLI | `panko`, `panko-admin` | `panko` with `install`, `dev`, `chart`, `admin`; `panko-admin` remains as a compatibility wrapper |
| CRD names | short name `db` for `databases` | no short names; category `panko` ([naming](naming.md)) |
| Certificates | regenerated by `make deploy` | stable CAs, daily renewal, reload without restart ([certificates](operations.md#certificates)) |

Unchanged: the API group `platform.example.com/v1`, resource identities (UIDs), the destroy
finalizer `metacontroller.io/compositecontroller-database-controller`, state Secrets in
`panko-state-<team>`, connection Secrets, gateway tokens and StateBackend bindings. v0.0.1 had no
remote runner pools, so there are no pool bindings to migrate.

## Migrating a v0.0.1 installation

Prerequisites:

- The v0.0.1 checkout that installed the cluster, with its `.local/kubeconfig` (`KC` below),
  `panko.json` and `.local/team-tokens.json`, and `helm` and `kubectl` (its `mise install`
  provides both).
- The `panko` v0.0.2 CLI ([installation](installation.md#get-the-cli)); `panko --version`
  prints `panko v0.0.2`.
- The cluster can pull `ghcr.io/hingst-it/panko-server:0.0.2` and
  `ghcr.io/hingst-it/panko-module-mirror:0.0.2`, or you mirror them and set `images.*` values.
- No Database is being created, updated or deleted, and API clients are stopped. The
  installation is paused from step 2 until step 4 applies the chart, which starts the embedded
  controller; nothing reconciles in that window.

```sh
# 1. Back up with the v0.0.1 tooling (private directory, outside the repository).
make backup BACKUP_DIR=$HOME/panko-backup-v0.0.1
# 2. Pause: scales the controller and gateway to zero and waits for running Jobs.
panko admin --kubeconfig KC --config panko.json pause
# 3. Remove the separate Metacontroller. Its CRDs, the CompositeController and the Databases'
#    finalizers stay; the embedded controller continues with the same finalizer.
helm --kubeconfig KC uninstall metacontroller --namespace metacontroller --wait
kubectl --kubeconfig KC delete namespace metacontroller
# 4. Install v0.0.2 over the existing objects.
panko install --kubeconfig KC --config panko.json --take-ownership \
  --tokens-file ./team-tokens.json --yes
# 5. Resume and remove the v0.0.1 onboarding Job, which the chart replaces.
panko admin --kubeconfig KC --config panko.json resume
kubectl --kubeconfig KC -n infra-backends delete job s3-onboard --ignore-not-found
```

Step 4 adopts namespaces, RBAC, Services, ConfigMaps, StatefulSets, Secrets' owners, the
CompositeController and the Metacontroller CRDs into the Helm release `panko-system/panko`, and
forces conflicts with `kubectl apply`'s field manager. It deletes and recreates only the stateless
Deployments that `kubectl apply` created (`database-hook`, `platform-gateway`, `runner-endpoint`,
`provider-mirror`, `module-mirror`). It applies the CRDs and removes the obsolete `db` short name.
Credentials are kept: the setup Job never replaces an existing Secret. Certificates switch to the
stable-CA model with an old+new CA bundle until their next renewal ([details](operations.md#legacy-ca-migration)).

Verify afterwards:

```sh
kubectl --kubeconfig KC get databases.platform.example.com -A   # every resource Ready
kubectl --kubeconfig KC get namespace metacontroller            # NotFound
panko --url ... --tokens-file ./team-tokens.json --team team-a get orders
```

The rehearsal checks that each resource keeps its UID, finalizers, `status.lastAppliedHash`, state
Secret, connection Secret and Job count (no re-apply happens), that the copied token file equals
`.local/team-tokens.json`, and that a later update and a complete destroy succeed.

From now on use the v0.0.2 CLI and `panko install` (or a GitOps tool) for this cluster, not
`make deploy` from the v0.0.1 checkout. To move to GitOps, see [GitOps](gitops.md#moving-an-installation).

### If the migration stops

- **Step 2 or 3 fails:** nothing has changed yet besides the pause. Fix the cause and continue,
  or `resume` to return to v0.0.1 (if the Metacontroller was already removed, reinstall it with
  `make bootstrap` from the v0.0.1 checkout first).
- **Step 4 fails** (missing permissions, an image the cluster cannot pull, a timeout): the output
  names the cause, for example `problem infra-runners/database-hook-... (image ...): ImagePullBackOff`.
  Fix it and rerun the same command; it resumes. A failure before the Helm release is applied
  (permissions, values, CRDs) leaves the installation paused. Once the release is applied, the
  chart runs the controller and gateway again (one replica each), even if `panko install` then
  fails waiting for another workload: resources are reconciled from that point on, and the pause
  of step 2 no longer holds. An interrupted run (Ctrl-C, lost connection) is resumed by the next
  `panko install`; see [troubleshooting](operations.md#troubleshooting).
- **Never** remove finalizers, state Secrets or the CompositeController to get past a failure:
  that drops the guarantee that infrastructure is destroyed before its resource disappears.

### Going back to v0.0.1

There is no automatic rollback. Code rollback is not automatically safe for stateful
infrastructure: v0.0.2 may already have applied changes, and v0.0.1 would not know about them.
Before any resource was updated under v0.0.2, the supported way back is a restore of the step-1
backup into a fresh v0.0.1 installation (v0.0.1's `make cluster-up bootstrap build deploy`, then
`make restore BACKUP_DIR=...`). After resources changed under v0.0.2, roll forward: fix the
problem in v0.0.2 instead.

## Routine upgrades of v0.0.2 and later

- **`panko install`:** install the new CLI and run the same `panko install` command. It applies
  the CRDs, reruns the setup Job, upgrades the Helm release with the chart embedded in that CLI
  (whose images default to the same version), and verifies readiness. Resources keep their
  bindings and state and are not re-applied; only a changed `module.revision` applies each
  resource once with the new module (with `module.rollout: manual`, only after
  `panko admin upgrade-module`).
- **Helm:** `helm upgrade panko oci://ghcr.io/hingst-it/charts/panko --version NEW -n panko-system ...`
  after applying the new chart's CRDs: `helm show crds oci://ghcr.io/hingst-it/charts/panko --version NEW | kubectl apply --server-side -f -`.
- **GitOps:** change the pinned chart version ([GitOps](gitops.md#upgrades-crds-pruning-and-persistent-data)).

A new module revision is fetched by the module mirror before the new mirror pod reports ready, and
runner Jobs retry fetching from the mirror for up to 90 seconds, so an upgrade does not cause
`module_fetch` failures. A failed upgrade is not rolled back automatically: Panko's state lives in
its own objects, and rerunning the upgrade resumes. Do not use `helm rollback` to an older chart
across a release boundary; restore a backup instead, as above.

## Backup and restore

A backup is consistent while the installation is paused. Without a checkout, with the v0.0.2 CLI:

```sh
export KUBECONFIG=./config
B=$HOME/panko-backup-$(date +%Y%m%d); mkdir -m 700 "$B"
panko admin --config cluster pause
panko admin --config cluster export --dir "$B"
kubectl -n infra-backends exec postgres-0 -- pg_dumpall -U postgres --clean --if-exists > "$B/postgres.sql"
# Only with installation.s3:
kubectl -n infra-backends exec s3-0 -- tar -C /data -cf - . > "$B/s3.tar"
panko admin --config cluster resume
```

`cluster.json` holds the Databases (spec, status and identity), StateBackends, BackendProfiles,
state and checkpoint Secrets, credentials (PostgreSQL admin, S3, gateway tokens) and the
installation ID. The directory contains credentials and database contents: keep it private and
out of any repository.

Restore into a **fresh** installation with the same values (`panko install` on a new cluster, or
`panko dev up` for a lab); `import` refuses a cluster that already has foreign Databases. Run the
restore as a script, so that it stops at the first error and the installation stays paused:

```sh
#!/usr/bin/env bash
set -euo pipefail
export KUBECONFIG=./config B=$HOME/panko-backup-20261029
trap 'echo "restore failed; the installation stays paused; fix the cause and rerun this script" >&2' ERR
panko admin --config cluster pause
panko admin --config cluster import --dir "$B"
grep -vxE 'DROP ROLE IF EXISTS postgres;|CREATE ROLE postgres;' "$B/postgres.sql" |
  kubectl -n infra-backends exec -i postgres-0 -- psql -U postgres -d postgres -q -v ON_ERROR_STOP=1 > "$B/restore-psql.log" 2>&1
if [ -f "$B/s3.tar" ]; then
  kubectl -n infra-backends exec -i s3-0 -- tar -C /data -xf - < "$B/s3.tar"
  kubectl -n infra-backends rollout restart statefulset/s3
  kubectl -n infra-backends rollout status statefulset/s3 --timeout=180s
fi
panko admin --config cluster --tokens-file ./team-tokens.json ensure-gateway-auth
trap - ERR
panko admin --config cluster resume
kubectl -n infra-gateway rollout restart deploy/platform-gateway
```

A checkout runs the same steps as `make backup` / `make restore` (`cluster/backup.sh`,
`cluster/restore.sh`; `PANKO_ADMIN="panko admin --config cluster"` uses a released CLI).
Restored Databases get new UIDs; `status.identity` keeps the original one, so names, state keys
and checkpoints stay the same. Each Database applies once against its restored state without
recreating databases or roles. A failed restore stays paused; rerunning `import` with the same
directory continues. `test/restore_rehearsal.sh` rehearses backup, loss of the cluster, a fresh
installation through `panko install`, restore, verification, update and delete.

The supported recovery path for a damaged installation is restore into a fresh installation. A
backup describes the infrastructure at the time it was taken: restoring an old backup after the
infrastructure changed makes state and reality disagree, and the next apply acts on that
difference. Check with `panko plan NAME --wait` before resuming normal changes.
